# OpenHealth-CDI Release and Reproducibility
## 1. Purpose of this document
This document defines what constitutes a stable OpenHealth-CDI research release and what another engineer should be able to reproduce from that release. It also defines which execution differences are expected and must not be mistaken for failures of reproducibility.
OpenHealth-CDI is a research reference implementation rather than a packaged production application. Releasing it therefore means more than assigning a version number to source code. A useful release must bind together a specific source revision, governance policy, architecture, documentation set, executable conformance suite, analytical configuration, scenario semantics, and citation record.
The intended result is an archival point from which another technically competent team can reconstruct the implementation, understand the authority and trust-boundary assumptions, execute the same scenarios, and determine whether the same architectural invariants hold.
Reproducibility in this repository does not mean that every generated byte must be identical between executions. Governance envelopes contain new identifiers, DPoP contains fresh timestamps and request identifiers, decision evidence contains execution timestamps, federated learning contains stochastic computation, and the Mode 1B reasoning runtime is not intrinsically deterministic. The reproducible object is therefore the **system behaviour under the documented relations and constraints**, not the accidental identity of every runtime artefact.
## 2. What is being released
The stable release contains the complete source and documentation required to describe the delivered OpenHealth-CDI reference implementation for three executable scenarios.
The A+B baseline demonstrates the founding federation between Hospitals A and B, governed federated training, issuer-owned capability, holder-bound model access, admission, and evidence.
Mode 1A demonstrates sponsored contribution through Charlie and Hospital C without converting Hospital C into a founding member or granting model-consumption authority through contribution.
Mode 1B demonstrates Hal as a bounded computational participant whose execution environment, reasoning runtime, transformation authority, and derivative-release path remain subordinate to federation governance.
The release therefore represents one coherent executable architecture rather than three independent demonstrations.
## 3. Release identity
The first stable research release is intended to use:
```text
version: 1.0.0
Git tag: v1.0.0
repository: https://github.com/onzelf/openhealth-cdi
license: GNU Affero General Public License v3.0
```
The release tag identifies the immutable source snapshot from which the archival release is reconstructed.
`CITATION.cff`, the GitHub release, the source tag, and any archival DOI record must all refer to the same released version.
The current `CITATION.cff` is prepared for a planned release date of:
```text
2026-09-01
```
If the actual release occurs on another date, `date-released` must be corrected **before** the release tag is created.
## 4. The release tag is the archival source boundary
Development branches are mutable. A release tag is not.
The `delivery` branch is used to assemble and validate the release candidate. Once the complete documentation, implementation, figures, manuscript artefact, citation metadata, and conformance status are accepted, one exact commit becomes `v1.0.0`.
After publication, the tag should not be moved to include a forgotten correction. A subsequent correction belongs to another commit and, where necessary, another release version.
This rule makes published evidence interpretable because another researcher can always resolve the exact source that was released.
> 🔑 **Takeaway**
> - `delivery` is a working branch.
> - `v1.0.0` is an archival statement about one exact commit.
> - Never move the release tag after publication merely to make history look cleaner.
## 5. What reproducibility means in OpenHealth-CDI
Reproducibility is defined at several levels because the system combines deterministic governance logic, distributed computation, cryptographic freshness, and an external reasoning runtime.
**Structural reproducibility** means that another deployment can reconstruct the same component responsibilities, trust boundaries, issuer relationships, governance policy, scenario roles, and execution apertures.
**Governance reproducibility** means that the same governed relations produce the same expected classes of ALLOW and DENY decisions and that authority cannot be enlarged through another execution path.
**Scenario reproducibility** means that A+B, Mode 1A, and Mode 1B retain the same participation semantics.
**Analytical reproducibility** means that the documented PathMNIST partition and training configuration can be rerun and produce a functioning model with the expected experiment structure. It does not imply bit-identical stochastic model weights unless a test explicitly requires such identity.
**Mode 1B reasoning reproducibility** means that the configured reasoning runtime participates through the same bounded contract and that the contextual scenario produces the expected governed action relation. It does not require an identical natural-language rationale from the LLM.
These levels are complementary. A system that reproduces a similar accuracy curve while removing issuer-owned capability assignment has not reproduced OpenHealth-CDI.
## 6. What must remain invariant
A conforming reproduction must preserve the central authority relations described by the release.
Hospitals A and B remain the founding organisations and the constitutive quorum remains policy-owned.
Hospital C remains a sponsored contributor relation rather than becoming an equivalent founding member.
Issuer-owned entitlement assignment remains distinct from caller request parameters.
Holder identity remains cryptographically bound to capability exercise.
Admission remains distinct from authentication and execution.
Contribution remains distinct from model consumption.
Hal remains the governed computational participant rather than the reasoning runtime.
Hal's execution path does not provide privileged federation authority outside the admitted path.
Rebind remains distinct from requester derivative consumption.
Source and derivative remain separately governed resources.
Model provenance remains distinct from the governance envelope controlling a later operation.
Signed decision evidence remains available for the relevant ALLOW and DENY outcomes.
These are the principal reproducibility targets.
## 7. What is expected to change between executions
Several values should normally differ between independent executions.
A newly established governance envelope receives another identifier.
KYO verification sessions and codes change.
ECT validity times change.
DPoP `iat`, `jti`, nonce, and signatures change.
Decision evidence timestamps and identifiers change.
Container and network addresses can change.
A newly trained neural network can produce different model bytes and slightly different metrics.
An external LLM can produce different wording in its rationale.
A cloud port can replace Docker networks, local storage, and host publication with different infrastructure mechanisms.
These differences do not invalidate reproducibility when the documented invariant remains observable.
## 8. What must not change silently
Some differences are not ordinary runtime variation.
Changing the founding participant set changes governance.
Changing the A+B quorum changes governance.
Giving Charlie model-query authority changes Mode 1A.
Giving Hal `query_model`, `submit_update`, or privileged governance authority changes Mode 1B.
Changing requester source scope changes the contextual experiment.
Removing holder binding changes the capability model.
Allowing execution after an expected Gatekeeper DENY changes the architecture.
Releasing a derivative without separate requester admission changes the architecture.
Replacing the Mode 1B reasoning model while claiming direct first-port equivalence changes an experimental dimension.
Collapsing model provenance into current governance-envelope state changes the evidence model.
Such changes require explicit documentation and new conformance analysis.
> ⚠️ **Interpretation constraint**
> - Different identifiers or stochastic outputs are normal.
> - Different authority relations are not normal execution variance.
## 9. Reproducibility is not bitwise identity
The release makes no general claim that independently trained PathMNIST models will have identical binary hashes.
GPU kernels, library implementations, floating-point execution, random-number use, container/runtime versions, and hardware can introduce variation even when the documented experiment configuration is preserved.
Model hashes are nevertheless useful inside tests that verify that a governance-only operation did not mutate an existing model. In that context the comparison is between a model before and after one operation in the same deployment.
That test must not be misread as a promise that another independent training run will generate the same hash.
## 10. Reproducibility of the PathMNIST partition
The PathMNIST partitioning rules are part of the experimental configuration.
The release records the partition profile and seed used by the reference deployment. The deterministic partition test verifies the intended relationship among Hospital A, Hospital B, and Hospital C data allocations.
A reproduction should preserve these rules when reproducing the published experiment.
A future investigation may intentionally use another partition. That creates another experiment rather than reproducing this one.
## 11. Reproducibility of model metrics
Training metrics should be treated as analytical observations rather than exact architectural acceptance values unless a particular test explicitly declares a numerical threshold.
The relevant reproduction requirement is that the configured federated training process executes with the intended participants and produces a usable model artefact and expected evidence structure.
Differences in the last decimal places of accuracy or loss do not constitute governance failure.
A substantial analytical deviation should nevertheless be investigated because it may reveal changed data partitioning, runtime configuration, library behaviour, or failed participant execution.
## 12. Reproducibility of Mode 1B reasoning
The Mode 1B contextual experiment uses an external reasoning runtime. The runtime receives requester and resource context together with a finite set of actions made available by Hal.
The release does not claim that the LLM's prose rationale is deterministic.
The reproducibility target is the bounded interaction contract and the expected contextual action relationship represented by the Mode 1B conformance test.
For the reference contextual matrix:
```text
Audrey + mucus
    direct source path

Audrey + colorectal adenocarcinoma epithelium
    governed derivative path

Bob + colorectal adenocarcinoma epithelium
    direct source path

Bob + mucus
    governed derivative path
```
The same Hal identity remains the governed participant in all four cases.
A future model comparison may deliberately change the reasoning runtime. That is a new experiment and should not be reported as a transparent reproduction of the released runtime behaviour.
## 13. External reasoning-provider availability
Reproducing the contextual Mode 1B experiment requires access to the configured external reasoning service or an explicitly documented equivalent backend.
The released source can describe the API contract and model configuration, but it cannot archive a third-party service or guarantee that the provider will expose the same model indefinitely.
The reproducibility record should therefore identify:
```text
reasoning provider
API family
model identifier
endpoint configuration
date of validation
```
Credentials must never be included.
The AWS port may use the Bedrock OpenAI-compatible Responses API while preserving the same model family and reasoning contract, as described in [AWS-PORTING.md](AWS-PORTING.md).
## 14. Secrets are deliberately not part of the release
A public research release must not contain the private credentials used by the running laboratory environment.
The repository intentionally excludes runtime secrets, private holder material, verifier mutable keys and state, certificate directories, OpenTofu state, and other local trust material.
Consequently, a public clone is not intended to be a byte-for-byte backup of the developer machine.
A reproducing team must provision its own valid trust material and external reasoning credential according to [DEPLOYMENT.md](DEPLOYMENT.md).
> 🔑 **Takeaway**
> - Reproducibility does not require publishing private keys.
> - It requires publishing enough architecture, configuration, code, and procedures to reconstruct the **same trust relationships with newly provisioned credentials**.
## 15. Never archive live private keys for convenience
Do not attach any of the following to a GitHub release or archival repository:
```text
OPENAI_API_KEY or another reasoning-runtime credential
private TLS keys
Hospital administrator private keys
Hub private key
issuer-proxy private key
human holder private keys
Hal private holder key
governance evidence-signing private key
terraform.tfstate containing sensitive values
private `.env` files
```
A reproducing environment should create or provision its own secrets.
Public certificates, public verification keys, schemas, configuration examples, and documented identity relationships can be preserved where they do not expose a private credential.
## 16. Runtime-generated state is not source
Governance envelopes, ECTs, DPoP proofs, mutable issuer registrations, execution sessions, temporary bind state, and other runtime artefacts are generated during an execution.
They should not normally be committed merely to make the repository look self-contained.
What the release must preserve is the code and configuration that determines how these artefacts are created and verified.
Where a particular evidence record is used as a publication artefact, it should be archived intentionally and with its provenance explained rather than by committing the entire mutable runtime state tree.

## 21. Check for unintentionally tracked sensitive material

```bash

  grep -Ei \
  '(^|/)(secrets|holder_keys|certs|keys)(/|$)|terraform\.tfstate|\.env$'
```

Some public non-secret artefacts can legitimately have names containing `keys` or `certs`, but private runtime material should not be tracked.
The absence of a result is not a complete secret scan. It is a useful repository-specific sanity check.

## 29. Release acceptance matrix
The release candidate should satisfy the following architectural evidence matrix.

| Area | Release acceptance |
| --- | --- |
| A+B constitution | policy-owned A+B participation and 2/2 quorum |
| federated training | complete A+B training lifecycle and inspectable model artefact |
| issuer authority | caller cannot select effective capability |
| holder binding | DPoP binding, replay and freshness behaviour remain effective |
| evidence | signed ALLOW and DENY records verify |
| Mode 1A | sponsored contribution succeeds without membership or query-right leakage |
| sponsorship | issuer, sponsor, provenance, and membership remain distinct |
| Mode 1B isolation | Hal uses intended Hub aperture and lacks privileged federation custody |
| Hal capability | bounded operations ALLOW while unrelated operations DENY |
| Table 7 | expected `DENY / ALLOW / ALLOW / ALLOW / DENY` |
| contextual Mode 1B | Audrey/Bob requester-resource matrix remains executable |
| derivative path | transformation and release remain separate admissions |
| provenance | current envelope does not rewrite model-run history |
| documentation | architecture, governance, scenarios, deployment and tests describe the tagged implementation |
| secrets | no live secret is intentionally included in the public release |

A failed architecture-relevant row blocks the stable release until the failure is understood.
## 30. Table 7 as a release-level Mode 1B signature
The five-case Mode 1B sequence provides a compact behavioural signature for the released bounded-agent architecture:
```text
requester unrestricted source     DENY
Hal bounded inference             ALLOW
Hal authorised rebind             ALLOW
requester derivative consumption  ALLOW
Hal privileged governance action  DENY
```
The significance lies in the combination.
A reproduction returning five ALLOW decisions has not reproduced bounded authority.
A reproduction returning five DENY decisions has not reproduced useful governed participation.
The mixed sequence demonstrates the intended boundary.
## 31. Contextual Mode 1B as a second release-level signature

## 32. Mode 1A as a release-level signature
Mode 1A should preserve:
```text
Hospital A + Hospital B
    founding collaboration

    Hospital A issuer

    guest contribution authority

    not a founding member
```

This combination prevents a superficially functional A+B+C training environment from being mistaken for reproduction of the governance architecture.
## 33. Preserve negative evidence
A release record should not present only successful operations.
Expected DENY results are part of the architecture and should be retained in the final validation record.
Examples include out-of-scope source requests, reserved resource access, caller-selected privilege, holder mismatch, replay, stale proof, Charlie model query, Hal ordinary model query, Hal training contribution, and Hal privileged governance operation.
Negative evidence defines the boundary around successful authority.

## 46. Reproducing without the original private state
A clean reproduction should not require the original developer's private keys, ECTs, KYO sessions, or governance envelope identifiers.
The reproducing team provisions new trust material, establishes a new A+B governance envelope, registers the required holders under its own local trust state, mints new ECTs, and produces new evidence.
The identifiers and signatures will therefore differ.
The governance relations and expected conformance behaviour should not.
This is the correct separation between reproducible architecture and non-transferable operational identity.

## 48. Reproduction outcome classes
A reproduction can be classified more precisely than simply "worked" or "failed".
**Conforming reproduction** means the documented architecture and required conformance outcomes are preserved.
**Operationally equivalent reproduction** means infrastructure mechanisms differ but preserve the same observable invariants, as intended for the AWS port.
**Modified experiment** means policy, participant relation, analytical configuration, reasoning model, or another material experimental dimension was intentionally changed.
**Non-conforming reproduction** means one or more architecture-relevant invariants are not reproduced.
This vocabulary helps prevent infrastructure improvements from being confused with governance changes.

A later release can change implementation details without invalidating the significance of `v1.0.0`.
If the architecture itself changes, the new release documentation should say explicitly which invariant changed and why.
Examples include adding another participation grade, implementing general delegation, changing the trust-boundary identity mechanism, introducing another derivative type, replacing the reasoning model as part of a deliberate experiment, or changing the constitutive collaboration.
The value of the stable tag is that such evolution can be compared against an immutable earlier reference.

## 52. What the release does not certify
`v1.0.0` does not certify clinical effectiveness.
It does not certify production readiness, operational scalability, regulatory compliance, general-purpose AI-agent safety, complete containment of arbitrary code, or security against every adversarial environment.
It establishes a research reference implementation in which the documented federation architecture and behavioural invariants are executable and inspectable.
This limitation is part of reproducibility because another researcher must know precisely which claims the artefact is intended to support.
## 53. Release summary
An OpenHealth-CDI release is a frozen relationship among source, governance configuration, architecture, documentation, scenarios, executable evidence, and scholarly citation.
The release is reproducible when another engineer can reconstruct those relationships and observe the same classes of governed behaviour. It is not necessary for the second execution to recreate the original envelope UUID, signatures, timestamps, neural-network bytes, or LLM prose.
The central reproducibility criterion is therefore the same one that defines the architecture itself.
**Objects may be regenerated. Execution artefacts may differ. The authority-bearing relations and their observable invariants must survive.**
